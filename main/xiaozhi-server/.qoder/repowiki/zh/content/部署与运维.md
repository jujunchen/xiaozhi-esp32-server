## 部署方案

本系统提供两种基于Docker的部署方案，分别适用于不同规模和需求的生产环境。

### 基础服务部署 (docker-compose.yml)

`docker-compose.yml` 文件用于部署核心服务，适用于资源有限或仅需核心语音交互功能的场景。该部署方案仅包含 `xiaozhi-esp32-server` 服务，不依赖外部数据库或缓存服务。

**关键配置说明：**
- **镜像源**: 使用 `ghcr.nju.edu.cn/xinnan-tech/xiaozhi-esp32-server:server_latest` 作为基础镜像。
- **端口映射**: 将容器内的 `8000` 端口（WebSocket服务）和 `8003` 端口（HTTP服务）映射到宿主机的相同端口。
- **环境变量**: 设置 `TZ=Asia/Shanghai` 以确保容器内时区为中国标准时间。
- **卷挂载**: 这是部署中最关键的部分，确保了配置和模型的持久化：
  - `./data:/opt/xiaozhi-esp32-server/data`：将宿主机的 `data` 目录挂载到容器内，用于存储用户配置文件（如 `.config.yaml`）。
  - `./models/SenseVoiceSmall/model.pt:/opt/xiaozhi-esp32-server/models/SenseVoiceSmall/model.pt`：将宿主机的语音识别模型文件挂载到容器内，确保服务能正确加载模型。

### 完整生态部署 (docker-compose_all.yml)

`docker-compose_all.yml` 文件用于部署完整的生态系统，包含服务器、管理后台、数据库和缓存服务，适用于需要完整功能和管理界面的生产环境。

**关键配置说明：**
- **服务依赖**: `xiaozhi-esp32-server` 服务依赖于 `xiaozhi-esp32-server-db` (MySQL) 和 `xiaozhi-esp32-server-redis` (Redis)，并使用 `condition: service_healthy` 确保依赖服务健康后才启动。
- **管理后台**: `xiaozhi-esp32-server-web` 服务提供管理界面，通过 `8002` 端口暴露。
- **数据库**: 使用 `mysql:latest` 镜像，通过 `healthcheck` 确保数据库服务可用，并将数据目录 `./mysql/data` 挂载到容器内以实现数据持久化。
- **Redis**: 使用 `redis:8.0` 镜像，作为缓存服务。
- **环境变量**: 为管理后台服务配置了数据库连接字符串 (`SPRING_DATASOURCE_DRUID_URL`) 和 Redis 连接信息。
- **卷挂载**: 除了核心服务的配置和模型挂载外，还挂载了 `./uploadfile` 目录用于管理后台的文件上传。

### 生产环境最佳实践

为确保服务在生产环境中的稳定性和安全性，建议遵循以下最佳实践：

- **资源分配**: 根据 `requirements.txt` 文件中的依赖（如 `torch==2.2.2`），该服务对计算资源有一定要求。建议为容器分配至少 2 核 CPU 和 4GB 内存，特别是当使用大型语言模型（LLM）或语音识别模型（ASR）时。
- **网络配置**: 在 `docker-compose.yml` 中，服务通过 `8000` 和 `8003` 端口暴露。在生产环境中，应通过反向代理（如 Nginx）将这些端口映射到标准的 `80` (HTTP) 或 `443` (HTTPS) 端口，并配置 SSL 证书以加密通信。
- **安全加固**: 
  - 使用防火墙规则限制对 `8000` 和 `8003` 端口的访问，仅允许来自可信网络或设备的连接。
  - 在 `config.yaml` 中，`server.auth.enabled` 可以设置为 `true` 来启用认证，结合 `allowed_devices` 白名单机制，增强服务安全性。
  - 定期更新基础镜像和依赖库，以修复已知的安全漏洞。

## 运维监控

有效的监控是保障系统稳定运行的关键。本系统通过日志系统和性能计数器提供全面的运行时洞察。

### 日志系统

系统使用 `loguru` 库构建了强大的日志系统，其核心配置位于 `config/logger.py`。

**日志配置与格式：**
- **初始化**: `setup_logging()` 函数从 `config.yaml` 中读取日志配置，并根据 `log.log_level` 设置日志级别（默认为 `INFO`）。
- **输出格式**: 日志同时输出到控制台和文件（`tmp/server.log`）。控制台日志采用彩色格式，包含时间、版本、模块字符串、标签和消息，便于快速识别。文件日志则采用更详细的格式，便于后续分析。
- **模块字符串**: 日志系统通过 `build_module_string()` 函数动态生成模块字符串（如 `00000000000000`），该字符串由 `VAD`, `ASR`, `LLM`, `TTS` 等模块的缩写组成，用于标识当前激活的模块组合，是分析日志时的重要线索。

### 性能指标监控

`core/utils/output_counter.py` 模块提供了关键的性能指标监控功能，用于跟踪服务的使用情况。

**核心功能：**
- **每日输出字数统计**: 使用 `_device_daily_output` 字典记录每个设备（通过 `device_id` 识别）在当天的输出字数。
- **计数器管理**: `add_device_output()` 函数在每次生成文本时增加计数，`get_device_output()` 函数查询当前字数，`reset_device_output()` 函数在每天0点重置计数器。
- **输出限制检查**: `check_device_output_limit()` 函数用于检查设备是否超过预设的输出限制，可用于实现服务的配额管理。

这些指标可以与日志系统结合，用于分析用户行为、评估服务负载和实施资源控制。

## 故障排查

当服务出现问题时，可以按照以下指南进行系统性排查。

### 服务无法启动

1.  **检查端口占用**: 确认宿主机的 `8000` 和 `8003` 端口未被其他进程占用。可通过 `netstat -an | grep 8000` 或 `lsof -i :8000` 命令检查。
2.  **检查依赖**: 对于 `docker-compose_all.yml` 部署，确保 `mysql` 和 `redis` 服务已成功启动且健康。查看 `docker-compose logs` 输出，确认没有数据库连接或Redis连接错误。
3.  **检查配置文件**: 确认 `data/.config.yaml` 文件存在且格式正确。如果使用 `config_from_api.yaml`，请确保 `manager-api.url` 和 `manager-api.secret` 配置正确。

### 连接超时

1.  **检查网络**: 确认客户端与服务器之间的网络连接正常，可以互相 `ping` 通。
2.  **检查防火墙**: 确认服务器的防火墙（如 `iptables` 或云服务商的安全组）已放行 `8000` (WebSocket) 和 `8003` (HTTP) 端口。
3.  **检查服务状态**: 使用 `docker ps` 确认容器正在运行，并使用 `docker logs xiaozhi-esp32-server` 查看服务日志，确认服务内部没有错误。

### 语音识别失败

1.  **检查模型文件**: 确认 `models/SenseVoiceSmall/model.pt` 文件已正确下载并存在于宿主机的 `models` 目录下，且卷挂载配置正确。
2.  **检查ASR配置**: 在 `config.yaml` 中，检查 `selected_module.ASR` 的配置是否正确，并确保所选ASR提供者（如 `FunASR`, `DoubaoASR`）的密钥（`api_key`, `access_token` 等）已正确填写。
3.  **查看日志**: 在日志中搜索与 `ASR` 相关的错误信息，通常会明确指出是模型加载失败还是API调用失败。

## 系统更新与维护

为了安全地更新服务，建议遵循以下流程：

1.  **备份**: 在进行任何更新前，务必备份 `data` 目录和 `mysql/data` 目录（如果使用完整部署），以防止配置和数据丢失。
2.  **更新镜像**: 修改 `docker-compose.yml` 或 `docker-compose_all.yml` 文件中的镜像标签（如从 `server_latest` 更新到特定版本号），然后执行 `docker-compose pull` 下载新镜像。
3.  **滚动更新**: 执行 `docker-compose down` 停止旧服务，然后执行 `docker-compose up -d` 启动新服务。Docker会自动创建新容器并销毁旧容器。
4.  **验证**: 通过日志和测试用例验证新服务是否正常运行。
5.  **配置更新**: 如果更新了 `config.yaml` 的结构，需要相应地更新 `data/.config.yaml` 文件，并重启服务使其生效。

此流程确保了更新过程的可预测性和可恢复性。
